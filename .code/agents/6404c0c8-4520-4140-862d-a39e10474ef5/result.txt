# Plan

OpenClaw already has impressive breadth: roughly 50 extension packages, 4 app surfaces, a large `src/` core, and a very heavy automated validation footprint. The highest-value strategy is not “add more features everywhere,” but to reduce architectural coupling, consolidate state/config patterns, and increase confidence at the seams between gateway, plugins, UI, and native clients.

## Priorities

1. **Finish the plugin boundary cleanup and make it the repo’s primary architecture program.**  
The strongest hotspot is boundary leakage between core and plugins/UI. The plugin SDK entrypoint is very broad and even re-exports Discord extension internals, which is a layering smell rather than a stable SDK surface.  
Likely hotspots: [src/plugin-sdk/index.ts#L1](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/plugin-sdk/index.ts#L1), [src/plugin-sdk/index.ts#L64](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/plugin-sdk/index.ts#L64), [docs/refactor/plugin-sdk.md#L11](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/docs/refactor/plugin-sdk.md#L11), [src/plugins/loader.ts#L63](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/plugins/loader.ts#L63), [scripts/check-no-monolithic-plugin-sdk-entry-imports.ts#L62](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/scripts/check-no-monolithic-plugin-sdk-entry-imports.ts#L62)  
Why first: this unlocks maintainability, external pluginability, cleaner testing, and lower upgrade risk across the whole monorepo.  
Concrete signal: I found large numbers of `extensions/** -> src/**` imports, especially in Discord, Telegram, Slack, and WhatsApp, so the refactor plan in docs appears directionally correct but incomplete.

2. **Split config/state management into smaller subsystems with one canonical persistence model.**  
`config/io.ts` has accumulated defaults, env handling, migrations, validation, write safety, and audit responsibilities in one place. Separately, state persistence is fragmented: channel reliability state is still effectively in-memory, career data uses its own JSON singleton store, and memory has its own substantial storage stack.  
Likely hotspots: [src/config/io.ts#L1](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/config/io.ts#L1), [docs/refactor/strict-config.md#L12](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/docs/refactor/strict-config.md#L12), [src/channels/persistence/channel-state-store.ts#L110](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/channels/persistence/channel-state-store.ts#L110), [src/gateway/server-startup-channels-orchestrator.ts#L63](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/gateway/server-startup-channels-orchestrator.ts#L63), [src/career/persistence.ts#L33](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/career/persistence.ts#L33)  
Highest-value move: define one durable state strategy for gateway-adjacent systems and keep module-local stores thin adapters over it.

3. **Rationalize the control-plane surface and introduce contract generation where possible.**  
The gateway method list is already very large and manually curated, while MCP tools, UI controllers, CLI commands, and native clients appear to evolve in parallel. That raises drift risk and makes adding features expensive.  
Likely hotspots: [src/gateway/server-methods-list.ts#L4](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/gateway/server-methods-list.ts#L4), [src/mcp/tools/index.ts#L21](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/mcp/tools/index.ts#L21), [ui/src/ui/app-render.ts#L1](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/ui/src/ui/app-render.ts#L1)  
Inference: a portion of current complexity comes from maintaining the same capabilities across multiple surfaces rather than from the capabilities themselves.  
Recommendation: promote a single capability catalog and generate as much metadata, typing, docs stubs, and UI affordance shape as possible from that source.

4. **Shift testing investment from unit density to seam confidence.**  
The repo already has very high test volume, so the next gains likely come from cross-surface contract tests and fewer brittle ad hoc paths. The biggest code files are often tests, which suggests good coverage but also maintenance weight. Scripts and packaging flows appear much less directly tested.  
Likely hotspots: [docs/help/testing.md#L10](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/docs/help/testing.md#L10), [package.json#L227](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/package.json#L227), [package.json#L306](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/package.json#L306)  
Priority focus:
- plugin runtime compatibility tests
- gateway/UI/native protocol parity tests
- config migration and doctor golden tests
- release/install/script smoke tests  
Under-tested surface callout: `scripts/` has many critical release/build/test helpers but no colocated tests.

5. **Reduce build and DX friction by turning custom checks into first-class architecture tooling.**  
The root `package.json` contains a very large custom build/check matrix. That’s powerful, but it also means repo knowledge is encoded in shellable scripts rather than discoverable architecture primitives.  
Likely hotspots: [package.json#L217](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/package.json#L217), [package.json#L232](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/package.json#L232), [package.json#L275](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/package.json#L275)  
Recommendation: keep the checks, but group them into explicit profiles such as `core-boundaries`, `plugin-contracts`, `gateway-protocol`, `docs-integrity`, and `release-smoke`, with fast local defaults and slower CI tiers.

6. **Prune or tier the product surface instead of treating every subsystem equally.**  
OpenClaw spans gateway, channels, MCP, memory, career intelligence, UI, and three native platforms. That breadth is exciting, but it creates uneven maturity.  
Likely hotspots: [README.md](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/README.md), [src/career/persistence.ts#L1](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/career/persistence.ts#L1), [docs/web/control-ui.md](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/docs/web/control-ui.md), [apps/ios/README.md](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/apps/ios/README.md), [apps/macos/README.md](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/apps/macos/README.md)  
Inference: the repo would benefit from explicit maturity tiers such as `core platform`, `supported extensions`, and `experimental surfaces`, especially for career and some specialized extensions.

7. **Treat documentation drift as an engineering issue, not just a docs issue.**  
There is enough evidence of doc/code mismatch that this should be part of the platform plan. For example, `src/README.md` still says `memory/` is empty even though `src/memory/` is now substantial, and the channel persistence story is described more strongly than the implementation currently supports.  
Likely hotspots: [src/README.md#L213](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/README.md#L213), [src/memory/qmd-manager.ts#L1](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/memory/qmd-manager.ts#L1), [src/channels/persistence/channel-state-store.ts#L117](/Users/rish2jain/Documents/Documents%20-%20Mac%20Studio/Openclaw/src/channels/persistence/channel-state-store.ts#L117)  
Recommendation: add “living architecture docs” ownership and verify selected docs in CI against code-owned inventories.

## Sequence

**Near-term, 0-6 weeks**
- Complete a repo-wide boundary audit and publish a target layering map for `src`, `extensions`, `ui`, and `apps`.
- Start the plugin-runtime migration with the worst offenders first: Discord, Telegram, Slack, WhatsApp.
- Split `config/io.ts` into read, validate, migrate, and write modules without changing behavior yet.
- Add contract tests around gateway methods, plugin SDK/runtime compatibility, and Control UI protocol assumptions.
- Introduce maturity labels for extensions and major product surfaces.

**Mid-term, 1-3 months**
- Make plugin runtime the only supported path for connector access to core behavior.
- Implement real durable channel reliability persistence and unify transient state ownership.
- Generate capability metadata for at least gateway methods, MCP tools, and UI navigation from a shared source.
- Convert the root validation pipeline into named profiles with clear developer guidance and CI staging.
- Reduce large hotspot files by extracting cohesive modules from chat handling, config IO, plugin loading, and UI render orchestration.

**Longer-term, 1-2 quarters**
- Decide whether career intelligence remains a first-class platform pillar or moves behind an experimental boundary.
- Consolidate persistence around a small number of storage patterns instead of subsystem-specific stores.
- Move docs toward generated inventories for commands, methods, config schema, plugin manifests, and supported channels.
- Define a formal support matrix for extensions, apps, and install modes to focus maintenance effort.

## Risks and Validation

Main tradeoff: boundary cleanup and state consolidation will slow short-term feature work, especially for channels that currently rely on direct core imports. That is still worth it because the current shape pushes complexity into every future change.

Validation ideas:
- Track direct `extensions/** -> src/**` import count and make it trend to zero.
- Track hotspot file size and ownership for files like config IO, plugin SDK, plugin loader, chat handlers, and UI render.
- Add golden tests for plugin behavior parity before and after runtime migration.
- Add doc integrity checks for architecture inventories and config/method catalogs.
- Measure developer-loop impact with “fast local” versus “full CI” validation profiles.

Biggest simplification candidates:
- plugin SDK/runtime boundary
- config IO and doctor/migration flow
- manual control-plane registries
- fragmented persistence patterns
- oversized orchestration files in gateway and UI
